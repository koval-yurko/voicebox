Topic 1

TTS, STT and LLM: the difference

All three are neural networks. A neural network is a large set of numbers (weights) that turns an input into an output. The type of input and output is what makes them different.

Compare side by side

TTSSTTLLM
InputText, a voice sampleAudioText (tokens)
OutputAudioTextText (tokens)
Typical size80M – 2B parameters70M – 2B parameters0.5B – 400B+ parameters
Quality measureMOS (people rate the voice), speaker similarityWER (word error rate, lower is better)Benchmarks, human preference
Speed measureRTF, time to first audioRTF, delay of the final textTokens per second, time to first token
Main riskWrong words, robot tone, voice misuseWrong words in noise, wrong languageMade-up facts (hallucination)

RTF (real-time factor) is compute time divided by audio time. RTF 0.2 means 10 seconds of audio takes 2 seconds to make. RTF below 1 is fast enough for live use.

Topic 2b · from backend/backends/__init__.py

One interface, many engines

Every engine has its own file, but all engines of one type share the same set of methods. The rest of the app calls only these methods. It never calls model code directly.

The contract

Python calls this a Protocol: a list of methods. An engine does not inherit from it. It only needs methods with the same names. Click a type.

Three shared parts

ModelConfig
A record for each downloadable model: name, engine, Hugging Face repo, size in MB, languages, and flags (needs_trim, retries_runaway, supports_instruct, stream_adapter). The app reads the flags and does not ask the engine.
Factory
get_tts_backend_for_engine("kokoro") makes the engine on first use and keeps it. A lock stops two requests from making it twice. The imports sit inside the function, so a missing library breaks only its own engine.
base.py
Shared helpers: device choice (cuda, mps, cpu; VOICEBOX_FORCE_CPU=1 forces CPU), cache checks, download progress, voice prompt joining, and memory cleanup.

Why the engines differ

The product feature

Cloning a voice, preset voices, a style instruction, or a voice made from a text description. One generate() call cannot hide these differences. So the flags and the voice prompt carry them.

Size and speed

From about 300 MB (LuxTTS, Kokoro) to 8,000 MB (TADA 3B). A user picks a fast small model or a large natural one.

Languages and licence

LuxTTS: English only. Kokoro: 8. Chatterbox and OmniVoice: 23. OmniVoice weights are non-commercial, so it is never a default.

Library quirks

Each model has its own loader and sample rate. Some add noise after the end (needs_trim) or do not stop (retries_runaway).

Hardware

qwen and chatterbox have a PyTorch file and an MLX file. The code comment says MLX Chatterbox is 7–9× faster on a Mac. MLX also needs all calls on one thread.

Streaming style

STT engines stream in 3 ways: segmented, rolling or native. See topic 6.

Weak points. The factory is a long if/elif list. A new engine needs 3 edits: the engine dictionary, a ModelConfig function, and the factory branch. Some engines ignore instruct or seed without an error. Only the supports_instruct flag tells you.
Topic 3

Model formats

A model is a file (or a folder of files) with weights. The format says how the numbers are stored and which program can read them. Choose a runtime first. Then choose the format that this runtime reads.

Caution. A pickle file (.pt, .pth, .bin) can run code when you load it. Load files only from sources that you trust. Prefer .safetensors.

Quantization: make a model smaller

Quantization stores each weight with fewer bits. The file gets smaller and faster. The quality drops a little. Move the sliders to see the memory need.

Rule: file size ≈ parameters × bits ÷ 8. Add about 20% for activations and the KV cache. The real number depends on the context length.

Topic 5

Algorithms and approaches

Many designs exist. This list shows the main families. A new model is often a mix of two or more.

Try it: how an LLM picks the next word

An LLM gives a score to every possible next token. Sampling turns the scores into a choice. TTS models that predict audio tokens use the same step.

Prompt: "The capital of France is"

Low temperature: the top token wins nearly every time. High temperature: the choice is more random. Top-k removes the weak tokens first. Temperature 0 (greedy) always takes the top token.

Topic 6

Inference: streaming, parallel work, caching

Inference means to run a trained model. It is different from training, which changes the weights. Inference only reads them.

Streaming

Without streaming, the user waits for the full result. With streaming, the model sends small pieces as soon as they are ready. Set the numbers to see the effect on TTS.

Your repo has streaming for both directions. TTS sends audio pieces while it generates. STT has two styles, named in your commits:

  • Rolling window (Qwen3-ASR adapter): the model re-reads the last few seconds again and again. The text can change. The adapter sends interim text, then final text.
  • Native streaming (Voxtral Realtime adapter): the model is built to read audio in order. The text is append-only. Old words do not change.

Caching

Four caches matter. The first one gives the largest gain.

Count of token positions the model must process. Without the cache the work grows with n². With the cache it grows with n. The cost is memory.

Parallel work

MethodMeaningUse here
BatchingOne model call handles many requests togetherBiggest gain on a GPU server. Used by LLM servers (vLLM).
ThreadsSeveral tasks in one Python processPython has the GIL: only one thread runs Python code at a time. Heavy math in torch or MLX releases it.

async / awaitOne thread switches tasks while it waits for I/OFastAPI routes. Good for network, not for math.

In your repo. The commit 1ed9a69 says streaming TTS and custom STT run "on the shared MLX thread". MLX does not allow two threads to use the same GPU state at once. So the code sends all MLX work to one thread. Web requests stay async. Heavy work waits in a queue.
Topic 6b

Optimization options in the field today

Teams improve a model in 4 ways: make it faster, make it smaller (memory), make it respond sooner (latency), or make the output better. Filter by model type and by goal. Click a card to open it.

A sensible order

  1. Measure first. Record RTF, time to first audio or token, WER, and peak memory. Without numbers you cannot tell if a change helped.
  2. Free choices. Pick the right model size, set the language, keep the model loaded, and use the best device (MLX on a Mac, CUDA on NVIDIA).
  3. Cheap tricks. Quantize, use a caching layer, cut text into sentences, gate STT with VAD.
  4. Serving tricks. Batching, streaming, speculative decoding. These need more code or a special server.
  5. Training tricks. Distillation and fine-tuning. These cost the most. Use them last.
Caution. The gains on the cards are typical ranges from public reports. Your result depends on the model, the chip and the input. Test each change on your own data, and listen to TTS output after quantization.
In this repo (checked in the code): separate MLX engines for Apple Silicon, bf16 MLX weights, several model sizes for each engine, unload and cache-clear functions, an offline-first Hugging Face cache check, one worker thread for MLX, text trimming and chunk retry for runaway TTS, and 3 STT streaming styles. I did not check for VAD, batching or speculative decoding.

CUDA, MLX, containers and other names

Where the math runs

NameWhat it isWhere
CPUGeneral processor. Slow for big models. Works everywhere.All
GPUChip with thousands of small cores. Fast at matrix math.All
CUDANVIDIA software layer that lets programs use NVIDIA GPUsNVIDIA, Linux and Windows
ROCmAMD version of CUDA (repo has requirements-rocm.txt)AMD GPUs
Metal / MPSApple GPU layer. MPS is the PyTorch backend for it.Mac (Apple Silicon)
MLXApple array library made for Apple Silicon. Often faster than MPS. (requirements-mlx.txt)Mac only
VRAMGPU memory. A model must fit in it. Macs share one memory with the CPU (unified memory).

Your Mac uses MLX files (*_mlx_backend.py). A Linux server with NVIDIA uses PyTorch with CUDA. That is why the repo has two sets of backends and two requirement files.

Packaging names

venv
Virtual environment. A private folder of Python libraries for one project. Your repo has backend/venv.
pip / requirements.txt
The tool that installs libraries, and the list of libraries to install.
pyproject.toml
Modern project file: name, version, dependencies, tool settings.
.python-version
Says which Python version to use. Yours says 3.12.
Docker image
A frozen package with the OS files, Python and your code. Like a template.
Container
A running copy of an image. It is isolated from the rest of the computer. Start and stop it fast.
nvidia-container-toolkit
Lets a container use the host NVIDIA GPU. Without it, the container sees only the CPU. Docker on a Mac cannot use the Apple GPU.
PyInstaller
Packs Python and the code into one program. The file voicebox-server.spec does this for the desktop app.
Hugging Face Hub
A website that hosts models, like GitHub for models. A repo id looks like org/model-name.
FastAPI / uvicorn
The web framework and the server that run backend/app.py and routes/.
MCP
A protocol that lets an AI agent call tools. See backend/mcp_server/.
WebSocket / SSE
Two ways to push data from server to client while a task runs. Used for streaming audio and text.
Container or venv? Use a venv on your own computer. Use a container to ship the same setup to a server.
